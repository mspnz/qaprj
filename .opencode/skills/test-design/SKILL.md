# Purpose
Выполнять систематическое проектирование тестовой модели (набора позитивных, негативных и граничных тестовых сценариев для последующего экспорта сабагентом в Qase) на основе подтвержденных требований, бизнес-правил, ограничений и выявленных рисков.

# Inputs
Для применения skill необходимы:
- валидированный артефакт анализа требований (`requirement-review-artifact.json`);
- опционально — артефакт спроектированных задач (`jira-tasks-artifact.json`) для перекрестной привязки тестов к задачам (`linked_task_ids`);
- код целевого проекта в Qase (`qase_project_code`);
- **опционально (режим Self-Refine):** предыдущая версия `qase-test-model-artifact.json` и список замечаний от `orchestrator-agent` по результатам проверки Quality Gate 3 (QG-3).

Skill не должен самостоятельно искать отсутствующие входные данные во внешних источниках (Confluence, Qase) за пределами переданного контекста.

# Procedure
1. **Проверка режима запуска:**
   - Если переданы замечания QG-3 (режим Self-Refine): доработать тестовую модель в `qase-test-model-artifact.json` по замечаниям оркестратора (например, добавить недостающие `boundary`/`negative` сценарии, уточнить шаги или привязки), сохранив блок `metadata` и не изменяя уже экспортированные сценарии (`export_status: "exported"`).
   - Если это первичный запуск: выполнить шаги 2–9 полностью.
2. Перенести `confluence_page_id` и `run_timestamp` из `requirement-review-artifact.json` в блок `metadata` и добавить `qase_project_code`.
3. Изучить подтвержденные функциональные требования (`confirmed`), бизнес-правила (`BR-*`), ограничения (`CON-*`) и критерии приемки (`AC-*`) из входного артефакта (исключив требования со статусом `blocked` и зафиксировав их в `uncovered_requirements`).
4. Определить логическую структуру тестовой модели — разбиение на разделы (`suites`) по функциональным модулям.
5. Применить техники тест-дизайна (эквивалентное разделение, анализ граничных значений, таблицы принятия решений, переходы состояний) и спроектировать атомарные сценарии:
   - **позитивные сценарии (`positive`):** проверка основного потока (Happy Path) и всех альтернативных валидных потоков согласно бизнес-правилам и критериям приемки;
   - **негативные сценарии (`negative`):** проверка обработки невалидных данных, нарушений бизнес-правил, ограничений и некорректных действий;
   - **граничные сценарии (`boundary`):** проверка поведения системы строго на границах допустимых диапазонов значений, квот и численных лимитов.
6. Определить приоритет (`priority`: `high` | `medium` | `low`) каждого тестового сценария с учетом выявленных на этапе анализа рисков (`risks`).
7. Задать для каждого сценария обязательные атрибуты: название (`title`), предусловия (`preconditions`), пошаговые действия (`steps`: `step_number`, `action`, `test_data`, `expected_step_result`) и однозначный итоговый ожидаемый результат (`expected_result`).
8. Связать каждый тестовый сценарий с ID проверяемых требований (`linked_requirement_ids`) и ID задач (`linked_task_ids` из `jira-tasks-artifact.json`).
9. Построить матрицу покрытия (`coverage_matrix`) и сформировать `qase-test-model-artifact.json`, выставив новым элементам `export_status: "pending"`, `qase_suite_id: null` и `qase_id: null`.

# Rules
- Не создавать тестовые сценарии для поведения системы, которое не описано в подтвержденных требованиях, и для требований со статусом `blocked`.
- Не придумывать ожидаемый результат (`expected_result`), если реакция системы на условие не определена в требованиях или бизнес-правилах (при обнаружении такого пробела — зафиксировать его в `uncovered_requirements`).
- Не игнорировать выявленные бизнес-правила, ограничения и риски (каждое правило и численный лимит должны быть проверены).
- Не смешивать несколько независимых проверок в одном сценарии (соблюдать атомарность тест-кейсов).
- Не выполнять прямые вызовы API Qase и не создавать задачи в Jira в рамках этого скилла.
- Не выдавать предположения за подтвержденные требования.
- Не изменять исходные требования или задачи.
- Не выполнять действия, не относящиеся к проектированию тестовой модели.
