# Purpose
Выполнять систематическую декомпозицию подтвержденных требований (`confirmed`) из `requirement-review-artifact.json` и проектировать структурированный набор задач для команды разработки (для последующего экспорта сабагентом в Jira), обеспечивая полное покрытие функциональности и прозрачную трассируемость.

# Inputs
Для применения skill необходимы:
- валидированный артефакт анализа требований (`requirement-review-artifact.json`);
- ключ целевого проекта в Jira (`jira_project_key`);
- опционально — список существующих задач из проекта Jira (передается `task-design-agent` для предотвращения дубликатов);
- **опционально (режим Self-Refine):** предыдущая версия `jira-tasks-artifact.json` и список замечаний от `orchestrator-agent` по результатам проверки Quality Gate 2 (QG-2).

Skill не должен самостоятельно искать отсутствующие входные данные и обращаться к внешним источникам (Confluence, Jira) за пределами переданного контекста.

# Procedure
1. **Проверка режима запуска:**
   - Если переданы замечания QG-2 (режим Self-Refine): скорректировать задачи в `jira-tasks-artifact.json` согласно замечаниям оркестратора (например, устранить пересечения, дополнить `acceptance_criteria` или привязки к `REQ-ID`), сохранив блок `metadata` и не пересоздавая задачи со статусами `exported` и `existing`.
   - Если это первичный запуск: выполнить шаги 2–8 полностью.
2. Перенести `confluence_page_id` и `run_timestamp` из входного `requirement-review-artifact.json` в блок `metadata` и добавить `jira_project_key`.
3. Проанализировать входной артефакт и отфильтровать требования:
   - взять в работу только подтвержденные и непротиворечивые функциональные требования со статусом `confirmed`;
   - требования со статусом `blocked` исключить из проектирования задач и зафиксировать в массиве `coverage_summary.skipped_requirements` с указанием причин блокировки (`blocker_refs`).
4. Сгруппировать связанные функциональные требования (`REQ-*`), бизнес-правила (`BR-*`) и ограничения (`CON-*`) в логически завершенные задачи разработки.
5. Проверить спроектированные задачи на отсутствие пересечений и дублирования между собой, а также со списком существующих задач Jira:
   - если аналогичная задача уже существует в Jira, не создавать дубликат, а включить её в список со статусом `export_status: "existing"` и указанием реального `jira_issue_key`.
6. Для каждой новой задачи сформировать:
   - временный локальный идентификатор (`local_id`: `TASK-1`, `TASK-2`...);
   - краткое и понятное название (`summary`), отражающее цель задачи;
   - подробное описание (`description`), включающее функциональные требования, применимые бизнес-правила и ограничения;
   - проверяемые критерии приемки (`acceptance_criteria`).
7. Установить логические зависимости между задачами (`dependencies`) и привязать к каждой задаче ID исходных требований (`linked_requirement_ids`).
8. Сформировать `jira-tasks-artifact.json`, выставив новым задачам `export_status: "pending"` и `jira_issue_key: null` (для последующего экспорта сабагентом `task-design-agent`).

# Rules
- Не создавать задачи для функциональности, которая не описана в подтвержденных требованиях (`confirmed`).
- Не проектировать задачи по требованиям со статусом `blocked`.
- Не придумывать отсутствующие бизнес-правила, ограничения, критерии приемки или технические решения.
- Не выдавать предположения за подтвержденные требования.
- Не изменять смысл исходных требований при декомпозиции.
- Не создавать дубликаты задач или задачи с пустым `linked_requirement_ids`.
- Не выполнять прямые вызовы API Jira и не создавать тестовые сценарии в рамках этого скилла.
- Не выполнять действия, не относящиеся к проектированию задач.

    "jira_project_key": "PROJ"

  "tasks": [
    {
      "local_id": "TASK-1",
      "summary": "Краткое и понятное название задачи",

        "Проверяемый критерий приемки 2"
      ],
